## 1. 产品目标与范围

核心玩法为“七槽麻将堆叠消除”：玩家通过单块与双块组成副牌，填满四个副牌槽后进入听牌，组成将牌触发番型大招，并持续清理桌面。

MVP 仅验证核心规则、操作节奏、番型大招和固定关卡可解性。

不在 MVP 范围内：正式美术麻将模型、复杂特效、音效、局外养成、广告、联网、存档、排行榜、撤销、洗牌、移出道具、多关卡随机生成。允许使用引擎几何体构成有厚度的轻 3D 白膜牌块，以及仅影响表现的轻量物理；不得用物理碰撞或落点决定玩法结果。

## 2. 技术与最终验收环境

- 引擎：当前工程固定 Cocos Creator 3.8.8；升级须另行批准。
- 语言：TypeScript，严格模式。
- 目标平台：微信小游戏。
- 画面：竖屏，基准分辨率 720×1280；全部 UI、底槽和计番区使用 2D 图形与引擎文字，牌桌保持 2D 平面视觉；桌面牌块及移动/消除表现使用轻 3D 白膜。
- 轻 3D 的边界：牌块不可拆分；厚度、抬起、落位、短时反弹/翻转只属于表现。固定坐标、GroupID、blockedBy、底槽容量和胜负不受物理影响。Demo 必须验证真实引擎几何体和刚体表现，不能仅以 2D 缩放冒充完成。

开发交付必须依次通过以下环境；缺少任一项即不通过 MVP 验收：

1. Chrome 移动端模拟视角：仅用于底层规则与状态机的快速验证。
2. Cocos Creator 引擎内运行：验证场景、UI、输入与资源加载。
3. 微信开发者工具：验证微信小游戏编译、运行和基础性能。
4. 微信真机：至少一台主流手机完成实机流程、交互和性能测试。

逻辑判定硬性指标：从 `TouchEnd` 到状态机完成判定、数据更新并派发渲染更新事件，耗时必须小于 100ms。Chrome、开发者工具和真机均应记录该指标。

## 3. 牌池与 Block 模型

### 3.1 牌池

- 仅使用万、筒、条三种花色，点数为 1～9。
- 不使用风牌、箭牌、白板、花牌、季节牌。
- 任意“花色 + 点数”在固定关中最多出现 4 张。

### 3.2 Block

| Block 类型 | 组成 | 底槽占位 | 规则 |
|---|---:|---:|---|
| 单块 | 1 张牌 | 1 格 | 不可拆分 |
| 同牌双块 | 2 张完全相同牌 | 连续 2 格 | 不可拆分 |
| 顺子双块 | 2 张同花色连续牌 | 连续 2 格 | 不可拆分 |

- 顺子双块仅允许 1-2 至 8-9，不跨花色，不允许 9-1。
- 双块在桌面、底槽、动画和大招中始终作为一个 Block 处理。
- 底槽从左到右紧密排列；任何入槽、消除或结算后均立即向左压缩，不存在 `[块][空][块]` 状态。

## 4. 组合配方与判定

一次配方结算使用两个 Block；将牌是单独的胡牌结算，使用一个同牌双块或两个相同单块；将牌同组残块清理属于胡牌后的额外结算，不参与配方：

| 组合 | 合法配方 | 结果 |
|---|---|---|
| 吃 | 单块 + 顺子双块，三张同花色连续 | 形成 1 副 |
| 碰 | 单块 + 同牌双块 | 形成 1 副 |
| 杠 | 同牌双块 + 同牌双块 | 形成 1 副 |
| 将 | 一个同牌双块独立成将，或两个相同单块；仅听牌阶段 | 形成将牌并胡牌 |

判定规则：

1. 新 Block 入槽后，先检查包含该新 Block 的合法组合。
2. 若新 Block 同时可与多个旧 Block 组合，依次选择：最后入槽的旧 Block → 底槽最靠左 Block → Block ID 字典序较小者。
3. 一次组合结算后，继续扫描底槽剩余 Block；若存在合法组合，继续结算直到无合法组合。
4. 听牌阶段中，将牌优先于吃、碰、杠。未形成将牌但形成吃、碰、杠时，该副牌直接在底槽抵消，不进入已满的计番区。
5. 将牌始终是两张相同的牌，且只在听牌阶段成立，有两种合法形式：
   - 一个同牌双块独立成将（占 1 个 BlockID、两张牌）；
   - 两个相同单块成将（占 2 个 BlockID、两张牌）。
   顺子双块不能作将；已参与副牌的 Block 不能重复作将；一手胡牌因此使用 9 或 10 个不同 Block。
6. 未满四副时不能提前胡牌；桌面上存在同牌双块不等于已经胡牌，必须通过合法取牌进入听牌结算。
7. 第四副牌进入计番区时，若底槽已经存在合法将牌（同牌双块或两个相同单块），应立即将最新形成的合法将牌作为将牌并胡牌。
8. **将牌同组残块清理（R0.2）**：当胡牌使用一个同牌双块作为将牌时，根据该 Block 的真实 GroupID 找到同组另一个 Block；若它仍在桌面或底槽，则作为“将牌同组残块”整体清除（不要求其当前可点击，不拆分）。若同组伙伴已在副牌、将牌或 removed，则不重复清除。两个相同单块作将时不触发本项。该残块不是手牌、不是完整大招目标，不改变番型/威力/目标数量；禁止按牌面跨组清除或清除其他孤牌。
   清理后重算底槽压缩、组状态、遮挡与终局；普通胡牌仍不等于直接通关。

## 5. 状态机、容量、失败与通关

### 5.1 状态

| 状态 | 核心行为 | 退出条件 |
|---|---|---|
| 凑副 | 吃、碰、杠进入副牌槽 | 四副牌满进入听牌；失败进入失败态 |
| 听牌 | 将牌优先；其他副牌就地抵消 | 将牌成立进入胡牌快照；失败进入失败态 |
| 胡牌快照 | 锁定番型与大招目标 | 生成不可变快照后进入大招 |
| 大招 | 数据层立即结算，视觉可持续播放 | 无待结算大招后回凑副或通关 |
| 通关 / 失败 | 禁止取牌，显示结算 UI | 点击重开 |

### 5.2 容量与虚拟入槽

- 底槽容量固定为 7 格。
- 若新 Block 入槽后不超过 7 格，先入槽再判定。
- 若会超过 7 格，执行虚拟入槽：仅当该 Block 与当前底槽中的 Block 能立即形成合法组合或将牌时，允许逻辑入槽并直接结算；UI 不显示超过 7 格。
- 虚拟入槽失败时，拒绝点击，Block 保持在桌面并提示“空间不足”。
- 失败条件（R0.1 调整）：一次合法取牌完成组合、瞬胡、大招及稳定扫描后，底槽仍稳定占满 7 格且底槽无合法组合，立即失败；不再以“桌面仍有可救牌”为理由维持 7 格非终局。
- 本次入槽后立即组合、结算后不足 7 格：不失败。
- 6 格时点击可立即组合的双块：仍允许虚拟入槽；点击不能组合的双块：拒绝并提示空间不足，不因 6 格直接判负。
- 未满 7 格但无步可走：仍为 Stalled，不新增失败条件。

### 5.3 通关与重开

- 通关条件：桌面无未清除 Block，底槽无未结算 Block，且无待结算大招。
- 允许计番区保留未完成的副牌；通关时其数据直接清空，代表放弃未完成胡牌。
- 重开恢复本文件定义的静态固定布局、GroupID、遮挡、锁定、动画和底槽初始状态。
- `Seed=888` 仅为固定关卡版本标识；本 MVP 不在运行时随机生成布局。

## 6. 番型与大招

胡牌时由四副牌和一将牌构成。杠占一个副牌槽，因此总牌数为 14～18 张。

| 番型 | 条件 | 优先级 | 威力 |
|---|---|---:|---:|
| 清一色 | 四副牌与将牌全部同一花色 | 最高 | 消除 5 个完整 GroupID |
| 碰碰胡 | 四副牌均为碰或杠，且不满足清一色 | 第二 | 消除 2 个完整 GroupID |
| 平胡 | 其他合法胡牌 | 最低 | 消除 1 个完整 GroupID |

- 只取最高番，不叠加。
- 快照生成时立即锁定番型和目标 GroupID，后续动画不改变结果。
- 大招目标为未被点击过、完整存在的 GroupID；同一 GroupID 任一 Block 被取走后，永久标记为已破坏。
- 目标排序：当前最高可见层级优先，同层按 GroupID 字典序。
- 目标不足时，消除所有剩余完整目标组；该非推荐路径不保证可解，后续按正常失败规则处理。
- 大招动画不锁定全局 UI；仅锁定目标 Block。新输入属于下一轮逻辑；多个大招可视觉重叠，但逻辑按快照顺序队列结算。

### 7.3 推荐通关路径

1. 点击 G01、G02、G03、G04 的两个 Block，形成三碰一杠；计番区填满四副牌。
2. 点击 G05 的两个单块，形成将牌；本手为清一色，锁定并清除 G06～G10 五个完整 GroupID。
3. G11～G16 解锁后，点击 G11、G12、G13、G14，形成四副牌并进入听牌。
4. 点击 G15、G16；它们在听牌阶段形成两组吃并就地抵消，不进入计番区。
5. 桌面和底槽清空；计番区残留四副牌按通关规则清空，进入通关。

该路径中每次大招目标数量充足；不会触发目标不足降级。
